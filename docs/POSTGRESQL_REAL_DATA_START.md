# PostgreSQL real data start

Этот документ описывает старт первых реальных данных Nutag в PostgreSQL. Deploy-инструкция находится в `docs/STREAMLIT_CLOUD_DEPLOY.md`, общая модель хранения — в `docs/DATABASE_STORAGE.md`, порядок работ — в `IMPLEMENTATION_PLAN.md`.

## Принятое решение

Для первых реальных онлайн-данных выбран чистый старт в PostgreSQL без переноса SQLite.

Причина: реальных данных пока нет, поэтому перенос SQLite -> PostgreSQL сейчас создаст сложность без пользы. При этом миграции структуры БД нужны и уже выполняются через Alembic.

## Что покрывает Alembic

Alembic используется для изменения структуры БД:

- новые таблицы;
- новые колонки;
- индексы;
- связи и ограничения;
- изменение nullable/default там, где это безопасно;
- служебные преобразования данных, если они тесно связаны с изменением схемы.

При изменении моделей SQLAlchemy нужно добавлять новую миграцию в `migrations/versions`.

Проверка:

```powershell
.\.venv\Scripts\python.exe -m pytest
```

Для PostgreSQL smoke-check:

```powershell
$env:NUTAG_DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@HOST/DBNAME?sslmode=require"
.\.venv\Scripts\python.exe scripts\check_database_url.py
```

## Когда нужен отдельный data migration

Отдельный сценарий миграции данных может понадобиться позже, если уже будут реальные данные и изменится бизнес-логика хранения.

Примеры:

- старые заказы нужно разложить на новые статусы заказа, оплаты и резерва;
- старые агрегированные остатки нужно превратить в трассируемые партии;
- нужно пересчитать себестоимость старых партий после изменения модели расчёта;
- новые обязательные поля нельзя заполнить константой/default и нужно выводить их из старых записей.

Такой сценарий нужно проектировать отдельно: описать входные данные, преобразование, контрольные отчёты и rollback/backup.

## Рекомендуемый чистый старт

1. `done` Создать чистую PostgreSQL-БД для Nutag: `nutag_prod`.
2. `done` Создать отдельного runtime-пользователя приложения: `nutag_app`.
3. `done` Сделать так, чтобы приложение инициализировало схему именно через `nutag_app`, а не через owner/admin.
4. `done` Обновить Streamlit secrets на URL с `nutag_app`.
5. `done` Выполнить smoke-check.
6. `done` Проверить вход в Streamlit Cloud.
7. `done` Ввести контрольный минимальный набор данных: `Килограмм / кг`.
8. `done` Перезапустить приложение и убедиться, что данные сохранились и видны с другого устройства.
9. `done` Подтвердить backup/restore у Neon до ввода реальных данных.

Почему важно инициализировать схему через app-user: приложение запускает Alembic-миграции при старте. Для будущих изменений схемы runtime-пользователь должен иметь права на DDL для объектов Nutag или владеть ими.

## App-user

В Neon роли, созданные через Console/API/CLI, получают расширенные административные права `neon_superuser`. Для более ограниченного пользователя Neon рекомендует создавать роль через SQL-клиент и выдавать ей нужные права явно.

Минимальная идея для чистого старта:

```sql
CREATE ROLE nutag_app LOGIN PASSWORD 'replace-with-generated-password';
CREATE DATABASE nutag_prod OWNER nutag_app;
```

После этого `NUTAG_DATABASE_URL` должен указывать на новую БД и нового пользователя:

```toml
NUTAG_DATABASE_URL = "postgresql+psycopg://nutag_app:PASSWORD@HOST/nutag_prod?sslmode=require"
NUTAG_APP_PASSWORD = "replace-with-real-app-password"
```

Если используется уже существующая БД, созданная owner/admin пользователем, нужно отдельно проверить владельца схемы и таблиц. Иначе будущие Alembic-миграции могут упереться в права.

## Backup/restore

До ввода реальных данных нужно подтвердить, как будет восстанавливаться PostgreSQL.

Текущий механизм восстановления на Neon Free:

- Neon History window для instant restore, time travel и branching from past states.
- Текущее окно истории: 6 часов.
- Отдельные долгосрочные backups/scheduled backups на текущем тарифе не считаются настроенными.

Когда фиксировать точку восстановления:

1. Перед изменением структуры БД или Alembic-миграциями.
2. Перед массовой загрузкой или удалением данных.
3. Перед изменениями в Streamlit secrets, если они влияют на БД.
4. Перед переносом или массовым вводом реальных данных.

Как фиксировать точку:

1. Записать дату и время начала рискованного действия.
2. Использовать московское время и понятное описание причины.
3. Пример: `2026-07-06 15:30 MSK — перед загрузкой справочников`.
4. Убедиться, что это время попадает в 6-часовое History window.

Как восстанавливаться:

1. В Neon использовать instant restore, time travel или branch from past state на момент до ошибки.
2. Предпочтительно сначала создать branch из прошлого состояния и проверить данные там, а не сразу откатывать основную БД.
3. После проверки выбрать безопасное действие: перенести данные из ветки, заменить основную БД или повторить операцию вручную.

Как проверить восстановление:

1. Создать тестовую запись в приложении.
2. Зафиксировать время.
3. Удалить или изменить тестовую запись.
4. Создать branch/restore из состояния до удаления.
5. Проверить, что запись есть в восстановленной версии.
6. После проверки удалить тестовую ветку, если она больше не нужна.

Текущий статус: app-user, БД, smoke-check, Streamlit secrets, контрольная запись и backup/restore-регламент подтверждены.

## Контрольный ввод первых данных

Перед полноценной эксплуатацией ввести минимальный набор:

1. Единица измерения.
2. Ингредиент.
3. Упаковка.
4. Продукт.
5. Первая закупка ингредиента и упаковки.
6. Проверка текущих остатков.
7. При необходимости: заготовка, производство, фасовка, тестовый заказ.

После этого перезапустить Streamlit Cloud и проверить, что данные остались в PostgreSQL.
