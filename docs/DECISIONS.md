# Решения проекта Nutag

Этот файл хранит продуктовые и архитектурные решения, включая отказанные варианты. Оперативная очередь находится в `IMPLEMENTATION_PLAN.md`; подробная история изменений — в `docs/CHANGELOG_IMPLEMENTATION.md`; сопоставление с исходной постановкой — в `docs/REQUIREMENTS_AUDIT.md`.

## Статусы

- `active` — действует сейчас.
- `replaced` — заменено более поздним решением.
- `rejected` — явно отклонено.
- `later` — возможно позже, но не сейчас.
- `not in MVP` — не входит в текущий MVP.
- `legacy only` — может оставаться только для совместимости или старых отчётов.

## Активные решения

| Статус | Решение | Причина | Где отражено |
|---|---|---|---|
| `active` | Учёт запасов является партийным, не средневзвешенным. | Для реальной себестоимости нужно списывать конкретную закупку, заготовку или партию ГП. | `IMPLEMENTATION_PLAN.md`, `nutag/services/inventory.py` |
| `active` | При списании пользователь выбирает конкретный источник, а сервис проверяет тип, единицу, остаток и цену источника. | UI не должен быть единственным местом бизнес-проверок. | `AGENTS.md`, `nutag/services/*`, tests |
| `active` | Цена списания берётся из выбранной партии, а не из UI. | Иначе можно получить неверную себестоимость и потерять трассируемость. | `nutag/services/preparations.py`, `nutag/services/production.py`, `nutag/services/economics.py` |
| `active` | Заготовки и готовая продукция учитываются как трассируемые партии. | Нужно понимать остатки и себестоимость конкретных источников. | `IMPLEMENTATION_PLAN.md`, production/preparation services |
| `active` | Фасовка ГП является отдельным этапом. | Упаковка списывается отдельно, а нефасованный остаток может быть расфасован позже. | `pages/5_Фасовка_ГП.py`, `nutag/services/packing.py` |
| `active` | Производство фиксирует нефасованный выпуск; фасованный выпуск не создаётся внутри формы производства. | Это упрощает workflow и исключает дублирование упаковки/фасовки. | `IMPLEMENTATION_PLAN.md`, `pages/4_Производство.py` |
| `active` | Отходы учитываются на этапе заготовок, а не производства. | Для текущего процесса производственные отходы не ожидаются, а ингредиентные отходы важны в заготовках. | `IMPLEMENTATION_PLAN.md`, `nutag/services/preparations.py` |
| `active` | Заказ резервирует готовую партию и уменьшает "доступно к продаже"; фактическое списание отделено от резерва. | Нужно видеть физический остаток и резерв отдельно. | `nutag/services/inventory.py`, `nutag/services/orders.py` |
| `active` | Фактическая себестоимость и маржа заказов считаются по выбранным партиям ГП. | Нельзя подменять выбранную партию средними значениями. | `nutag/services/economics.py`, `pages/7_Экономика.py` |
| `active` | PostgreSQL является целевой БД для реальных данных и production-like проверки локально и онлайн. | Одна целевая СУБД снижает риск расхождений миграций, типов данных, ограничений и поведения между локальной разработкой и deploy. | `IMPLEMENTATION_PLAN.md`, `docs/DATABASE_STORAGE.md` |
| `active` | SQLite остаётся только dev/fallback-режимом. | Он удобен для быстрого запуска, тестов, демо и временной локальной работы, но не должен быть источником истины для production-like поведения. | `IMPLEMENTATION_PLAN.md`, `docs/DATABASE_STORAGE.md` |
| `active` | Подключение к БД задаётся через `NUTAG_DATABASE_URL`, если переменная окружения задана. | Это сохраняет локальный режим простым и оставляет путь к внешней БД без переписывания кода. | `nutag/db/session.py`, `docs/DATABASE_STORAGE.md` |
| `active` | Перед изменениями схемы SQLite создаётся backup рядом с рабочей БД. | Обновление версий не должно оставлять пользователя без возможности восстановить реальные данные. | `nutag/db/init_db.py`, `docs/DATABASE_STORAGE.md` |
| `active` | Streamlit-страницы подключаются к БД через общий runtime-helper. | Единая точка создания `engine`, инициализации схемы и `SessionLocal` снижает риск расхождения поведения между страницами. | `nutag/db/runtime.py`, `app.py`, `pages/*` |
| `active` | Онлайн-режим для одного пользователя является текущим приоритетом и должен использовать внешний PostgreSQL через `NUTAG_DATABASE_URL`/secrets. | В облачном deploy нельзя полагаться на SQLite-файл приложения как на устойчивое хранилище реальных данных. | `IMPLEMENTATION_PLAN.md`, `docs/DATABASE_STORAGE.md` |
| `active` | `NUTAG_DATABASE_URL` должен использовать отдельного PostgreSQL-пользователя приложения, а не владельца/администратора БД. | Секреты могут быть случайно раскрыты; отдельный пользователь с минимальными правами снижает ущерб и упрощает ротацию пароля. | `IMPLEMENTATION_PLAN.md`, `docs/DATABASE_STORAGE.md` |
| `active` | В Streamlit UI `NUTAG_DATABASE_URL` и `NUTAG_APP_PASSWORD` из root-level secrets поднимаются в окружение до инициализации БД; пароль без явной БД блокирует приложение. | Общий DB-helper читает окружение, а онлайн-приложение не должно молча использовать SQLite fallback при ошибке secrets. | `nutag/ui/auth.py`, `docs/DATABASE_STORAGE.md` |
| `active` | Онлайн-MVP требует минимальной защиты доступа для одного пользователя, но не полноценной регистрации и многопользовательской модели. | Реальные данные не должны быть доступны публично, но SaaS-авторизация преждевременна для текущего сценария. | `IMPLEMENTATION_PLAN.md` |
| `active` | Для первых реальных онлайн-данных выбран чистый старт в PostgreSQL без инструмента переноса SQLite -> PostgreSQL. | Реальных данных пока нет, поэтому перенос между СУБД сейчас добавит сложность без пользы; изменения структуры остаются на Alembic, а будущие сложные преобразования существующих данных проектируются как data migrations. | `IMPLEMENTATION_PLAN.md`, `docs/DATABASE_STORAGE.md`, `docs/POSTGRESQL_REAL_DATA_START.md` |
| `active` | План ведётся как `Execution Queue + Domain Backlog`. | Backlog по областям не должен подменять последовательность работ. | `AGENTS.md`, `.codex/skills/nutag-roadmap-maintenance/SKILL.md`, `IMPLEMENTATION_PLAN.md` |

## Решения по плановой экономике

| Статус | Решение | Причина | Где отражено |
|---|---|---|---|
| `later` | Амортизация оборудования должна считаться автоматически из стоимости и срока службы. | Ручной ввод суммы амортизации искажает плановую себестоимость. | `IMPLEMENTATION_PLAN.md` |
| `later` | Для MVP амортизация распределяется между продуктами пропорционально плановым месячным объёмам. | Это проще ручных долей и достаточно для первого расчёта цены. | `IMPLEMENTATION_PLAN.md` |
| `later` | Помощник цены должен показывать плановую себестоимость, амортизацию, маржу/наценку и рекомендуемую цену. | Пользователю нужно выбирать цену до закрытия месяца. | `IMPLEMENTATION_PLAN.md` |
| `later` | Машино-часы могут заменить распределение по объёму позже. | Это точнее, но преждевременно для MVP. | `IMPLEMENTATION_PLAN.md` |

## Отклонённые и заменённые решения

| Статус | Решение | Почему отклонено или заменено | Что делать вместо этого |
|---|---|---|---|
| `replaced` | Средневзвешенная цена как основной метод складского учёта. | Не даёт трассируемой себестоимости конкретной партии. | Партийный учёт и выбранный источник списания. |
| `legacy only` | Функции средневзвешенной цены и связанные старые тесты. | Могут быть полезны только для старой совместимости или legacy-отчётов. | Не использовать как источник истины для новых операций. |
| `rejected` | Ручной ввод цены списания при выбранной партии. | Пользователь может случайно подменить себестоимость. | Цена берётся из выбранной партии. |
| `rejected` | Списание в минус без явного сценария покрытия дефицита. | Разрушает складскую достоверность. | Блокировать или явно проектировать сценарий дефицита. |
| `rejected` | Сопоставление остатков только по совпадающим numeric ID. | ID разных сущностей могут совпадать. | Всегда учитывать тип сущности. |
| `rejected` | Фасовка и расход упаковки прямо в форме производства. | Смешивает производство и складскую фасовку, усложняет исправления. | Отдельная операция `Фасовка ГП`. |
| `rejected` | Отдельный учёт отходов на этапе производства. | Пользователь не планирует такие отходы; отходы есть на этапе заготовок. | Учитывать отходы ингредиентов в заготовках. |
| `rejected` | Ручной выбор оборудования и ввод часов работы на странице производства. | Амортизация должна быть плановой, а не произвольной строкой партии. | Справочник оборудования + плановые объёмы. |
| `rejected` | Ручной ввод суммы амортизации на единицу продукции. | Сумма должна выводиться из стоимости, срока службы и планового объёма. | Автоматический расчёт амортизации. |
| `not in MVP` | Ручное задание долей распределения амортизации между продуктами. | Дублирует информацию, которую можно получить из плановых объёмов. | Распределение по плановым месячным объёмам. |
| `not in MVP` | Полноценная регистрация, роли, многопользовательская работа и SaaS-инфраструктура. | Текущий сценарий — онлайн-доступ к реальным данным одного пользователя. | PostgreSQL и минимальная защита доступа сейчас; полноценная авторизация только после отдельного решения. |
| `not in MVP` | Импорт из Excel. | Не критично для текущего MVP. | Ручной ввод и отчёты в приложении. |
