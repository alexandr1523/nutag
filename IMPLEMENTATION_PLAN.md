# План реализации MVP Nutag

Документ фиксирует принятые продуктовые и технические решения для первой рабочей версии локального приложения учёта домашнего производства замороженных полуфабрикатов.

## 0. Статус документа и связь с функциональной постановкой

`IMPLEMENTATION_PLAN.md` не заменяет исходную функциональную постановку. Он является техническим планом реализации MVP на основе следующих документов:

- `README.md`;
- `README_FUNCTIONAL.md`;
- `01_scope_and_principles.md`;
- `02_registers_and_entities.md`;
- `03_calculation_rules.md`;
- `04_workflows_and_controls.md`.

Правила трактовки:

1. Исходные функциональные документы выше являются источником бизнес-требований.
2. `IMPLEMENTATION_PLAN.md` фиксирует технические решения, MVP-ограничения и уточнения, принятые после чтения функциональной постановки.
3. Если между `IMPLEMENTATION_PLAN.md` и исходной функциональной постановкой обнаружится противоречие, приоритет имеет исходная функциональная постановка до явного согласования изменения.
4. После согласования изменения нужно обновить либо функциональную постановку, либо этот план, чтобы убрать расхождение.
5. Если исходная постановка не описывает техническую деталь, решение из `IMPLEMENTATION_PLAN.md` считается допустимым уточнением, а не заменой бизнес-требования.

На момент добавления этого раздела явных противоречий между планом и исходными документами не обнаружено. Есть только уточнения реализации, которые исходная постановка намеренно не фиксировала: Streamlit как интерфейс, SQLite как хранилище, SQLAlchemy как слой доступа к данным, `pyproject.toml`, отсутствие импорта из Excel в MVP, упрощённая статусная модель заказов и правила обработки дефицита остатков.

## 1. Цель первой версии

Первая версия должна дать сквозной рабочий сценарий:

1. завести справочники;
2. завести закупку;
3. увидеть остатки сырья, упаковки и расходников;
4. создать заготовку;
5. списать сырьё на заготовку;
6. рассчитать себестоимость заготовки;
7. создать производственную партию;
8. списать сырьё, упаковку и заготовки на партию;
9. зафиксировать фактический выход готовой продукции;
10. учесть фасовки 0,5 кг и 1 кг;
11. создать заказ;
12. зарезервировать или списать готовую продукцию;
13. посчитать выручку, себестоимость проданного, маржу и базовую экономику;
14. показать основные ошибки и контрольные сигналы.

MVP строится вокруг сквозного потока, а не вокруг полной проработки одного изолированного модуля.

## 2. Технический стек

Для первой версии выбран следующий стек:

- Python;
- Streamlit для локального интерфейса;
- SQLite для локального хранения данных;
- SQLAlchemy для работы с базой данных;
- pandas для подготовки табличных данных и отчётов;
- openpyxl для экспорта в Excel;
- pytest для минимальных тестов расчётного ядра.

Зависимости и метаданные проекта будут оформлены через `pyproject.toml`.

## 3. Формат приложения

Первая версия — локальное Streamlit-приложение.

Предполагаемый запуск:

```bash
streamlit run app.py
```

Регистрация, авторизация, серверная инфраструктура и многопользовательская работа в MVP не закладываются.

## 4. Хранение данных и Excel

Основное хранилище данных — SQLite.

Excel используется только для экспорта:

- закупок;
- остатков;
- заготовок;
- производственных партий;
- заказов;
- экономики;
- полного отчёта по периоду.

Импорт из Excel в первой версии не реализуется, чтобы не усложнять контроль целостности данных и сопоставление справочников.

## 5. Интерфейс Streamlit

Выбран гибридный интерфейс:

- многостраничное Streamlit-приложение;
- внутри страниц используются вкладки для форм, списков и отчётов.

Предварительная структура страниц:

```text
app.py

  2_Закупки_и_остатки.py
  3_Заготовки.py
  4_Производство.py

  6_Экономика.py
  7_Экспорт.py
```

## 7. Справочники MVP

В первой версии нужны справочники:

- продукты;
- виды заготовок;
- варианты / начинки;
- ингредиенты;
- упаковка;
- расходники;
- единицы измерения;
- этапы производства;
- статусы заказов;
- статусы оплат;
- способы получения;
- причины списаний;
- категории постоянных расходов;
- оборудование.

## 8. Рецептуры

Рецептура — это план, а фактическое производство — отдельный факт.

Для рецептов поддерживаются разные базы расчёта:

- на 1 кг готового продукта;
- на 10 кг готового продукта;
- на 100 штук;
- на одну стандартную партию;
- на произвольную пользовательскую базу.

Рецепты должны поддерживать версии. Активная версия используется по умолчанию, но фактическая партия должна хранить ссылку на конкретную версию рецепта.

## 9. Закупки, остатки и средневзвешенная цена

Каждая закупка хранится отдельно. Цена ингредиента, упаковки или расходника не перезаписывается последним значением.

Для MVP используется метод средневзвешенной цены:

```text
средневзвешенная цена =
(начальная стоимость остатка + стоимость закупок)
/
(начальный остаток + купленное количество)
```

Эта цена используется для оценки списаний сырья, упаковки и расходников.

Минимальные тестовые сценарии для расчёта:

1. начальный остаток плюс закупки;
2. нулевой начальный остаток;
3. несколько закупок с разной ценой.

## 10. Дефицит остатка

Если операция уводит остаток в минус, приложение не должно молча сохранять отрицательный остаток.

Доступны только два варианта покрытия дефицита:

1. личные домашние запасы;
2. забытая закупка.

Вариант «временный дефицит / уточнить позже» в MVP не используется.

### 10.1. Личные домашние запасы

Если бизнес использовал личный ресурс, пользователь указывает оценочную цену.

Такое внесение:

- увеличивает управленческую себестоимость;
- показывается отдельно как неденежный расход;
- не считается обычной денежной закупкой;
- не создаёт долг бизнеса владельцу в MVP.

### 10.2. Забытые закупки

Если дефицит возник из-за забытой закупки, пользователь создаёт обычную закупку задним числом или через быстрый сценарий добавления пропущенной закупки.

Такая закупка участвует в остатках и средневзвешенной цене как обычная закупка.

## 11. Личное потребление из бизнеса

Нужно учитывать обратный поток: из бизнес-запасов можно взять сырьё, упаковку, расходники, заготовку или готовую продукцию для личного пользования.

Правило MVP:

- личное потребление списывается по себестоимости;
- не считается продажей;
- не попадает в маржу клиентских заказов;
- отдельно уменьшает итоговый результат периода после операционной прибыли.

В отчётах нужно разделять:

1. маржу клиентских заказов;
2. операционную прибыль до личного потребления;
3. личное потребление по себестоимости;
4. итог после личного потребления.

## 12. Заготовки

Заготовка — внутренний полуфабрикат, который может быть использован в одной или нескольких будущих партиях.

Себестоимость заготовки включает:

- использованные ингредиенты;
- материалы и упаковку, если применимо;
- трудозатраты подготовки;
- прочие прямые расходы.

Если заготовка сделана с запасом, в финальную партию переносится только стоимость фактически использованной части.

## 13. Производственные партии

Каждая готовка фиксируется как отдельная производственная партия.

Партия может использовать:

- обычные ингредиенты;
- упаковку;
- расходники;
- заготовки;
- трудозатраты;
- амортизацию оборудования, если она включается;
- долю постоянных расходов, если она включается.

Фактическая себестоимость считается по фактическому выходу, а не по плановому.

## 14. Готовая продукция и фасовки

Готовая продукция учитывается одновременно:

- в упаковках;
- в килограммах.

Например:

```text
12 упаковок × 0,5 кг = 6 кг
8 упаковок × 1 кг = 8 кг
```

При фиксации выхода партии система должна сверять суммарный вес фасовок с фактическим выходом партии.

## 15. Заказы, партии и резервирование

Заказ может быть:

1. без привязки к партии;
2. привязан к планируемой партии;
3. привязан к фактической партии после производства.

Резервирование готовой продукции настраивается по заказу.

Правило по умолчанию:

- резервировать после оплаты.

Исключение:

- для готовой маленькой партии «в наличии» можно вручную зарезервировать заказ с оплатой при получении.

## 16. Списание готовой продукции на заказы

Если есть несколько партий одного продукта, система предлагает партию автоматически, но пользователь может изменить выбор вручную.

Правило подбора:

1. FEFO — сначала партия с ближайшей датой «использовать до»;
2. FIFO — при равных сроках сначала более старая партия;
3. ручная корректировка пользователем при необходимости.

Себестоимость проданного считается по себестоимости выбранной партии.

## 17. Статусная модель заказов

Для MVP используется упрощённая модель из четырёх статусных полей.

### 17.1. `order_status`

- новый;
- подтверждён;
- готов к выдаче;
- выдан;
- отменён.

### 17.2. `payment_status`

- ожидает оплаты;
- оплачен;
- оплата при получении;
- возврат.

### 17.3. `reservation_status`

- не зарезервирован;
- в плановой партии;
- зарезервирован;
- частично зарезервирован;
- резерв снят.

### 17.4. `has_problem`

- да;
- нет.

Отдельные ручные статусы производства и выдачи в MVP не вводятся. Они выводятся из связанных данных: партии, резерва, окна выдачи, даты фактической выдачи и контрольных ошибок.

## 18. Экономика и отчёты

Минимальный экономический блок должен показывать:

- выручку клиентов;
- себестоимость проданного клиентам;
- маржу клиентских заказов;
- расходы на доставку и выдачу;
- постоянные расходы;
- операционную прибыль до личного потребления;
- личное потребление по себестоимости;
- итог после личного потребления;
- точку безубыточности;
- окупаемость оборудования;
- повторные покупки;
- план-факт.

## 19. Контрольные сигналы MVP

Система должна явно показывать проблемы:

- отрицательный остаток сырья;
- отрицательный остаток упаковки;
- отрицательный остаток заготовок;
- отрицательный остаток готовой продукции;
- закупка без цены;
- закупка без количества;
- партия без фактического выхода;
- заготовка без фактического выхода;
- заказ без цены;
- оплаченный заказ без суммы;
- выданный заказ без статуса оплаты;
- расход без связанной партии или заготовки;
- оборудование без срока использования, если оно включено в амортизацию.

## 20. Минимальные тесты

Streamlit-интерфейс в MVP не тестируется автоматически.

Минимальные тесты нужны для расчётного ядра:

- средневзвешенная цена;
- себестоимость заготовки;
- себестоимость производственной партии;
- маржа заказа;
- личные внесения;
- личное потребление;
- движение остатков.

## 22. Доработки и уточнения (MVP Refinements)

Ниже зафиксированы требования по улучшению функциональности, выявленные в ходе первых итераций разработки.

### 22.1. Удобство ввода закупок
- **Масштабируемость:** Увеличить количество позиций, вводимых за один раз (сейчас 5).
- **Гибкость цены:** Возможность ввода либо цены за единицу, либо общей стоимости позиции с автоматическим пересчётом второго поля.
- **Предварительный пересчёт суммы:** В разделе `Закупки и остатки` при вводе количества и цены по каждой позиции `Итого` должно пересчитываться сразу в форме, до сохранения документа.

### 22.2. Расчёт себестоимости и Труд
- **Трудозатраты:** Ввод труда в часах (или минутах). Стоимость часа должна задаваться в настройках или справочнике и автоматически пересчитываться в денежный эквивалент для заготовок и партий.
- **Автоматизация цен ингредиентов:** На этапе создания заготовки цены не вводятся вручную. Система должна автоматически подтягивать средневзвешенную цену из актуальных остатков.
- **Отображение стоимости ингредиента в заготовках:** На вкладке `Заготовки` в строках ингредиентов вместо отдельного поля `Цена` нужно показывать стоимость выбранного ингредиента с учётом введённого количества. Поле должно быть визуально соразмерно остальным элементам строки и выровнено по их уровню.
- **Амортизация:** Вместо ручного ввода амортизации на каждую партию, внедрить автоматический расчёт (например, на основе стоимости оборудования и срока его службы, распределяя на количество часов работы или фиксированную сумму на кг продукции).

### 22.3. Учёт потерь и фасовки
- **Мясная обрезь (Потери):** Добавить поле для учёта "выхода" или "процента потерь" при первичной обработке сырья (например, срез жира/жил с мяса).
- **Частичная фасовка:** Реализовать логику, при которой не вся продукция партии фасуется сразу. Остатки должны храниться как "нефасованная готовая продукция" и учитываться в балансе.

### 22.4. Складской учёт и Контроль
- **Полные остатки:** Видимость остатков должна включать: ингредиенты, внутренние заготовки и готовую продукцию (фасованную и нефасованную).
- **Контроль на этапе заготовок:** Проверка наличия ингредиентов должна происходить не только при финальном производстве, но и при создании промежуточных заготовок.
- **Списание в реальном времени:** Списание остатков должно происходить сразу после фиксации факта заготовки или производства.

### 22.5. Редактирование данных
- **Корректировка истории:** Реализовать возможность редактирования и удаления ошибочно введённых закупок, заготовок и партий с автоматическим пересчётом зависимых остатков и цен (там, где это технически возможно без нарушения целостности).

### 22.6. Интерфейс и Системные функции
- **Единицы измерения:** Внедрить автоматическую конвертацию (например, граммы в килограммы) там, где это необходимо для удобства ввода.
- **Фиксация единицы измерения в справочнике:** Для каждого ингредиента, упаковки и расходника единица измерения должна задаваться в справочнике как основная и затем автоматически подставляться во всех формах, где используется этот элемент.
- **Точность отображения по единицам:** Для каждой единицы измерения нужно задавать в справочнике количество знаков после запятой для отображения. Эта настройка должна автоматически применяться во всех формах и списках, где используется данная единица.
- **Редактирование единиц измерения:** В справочнике единиц должна быть возможность изменять существующие единицы, включая название, сокращение и параметры отображения.
- **Завершение работы:** Добавить кнопку корректного выхода из приложения.

### 22.7. Новые уточнения и вопросы
- **Авто-цены и выбор партий:** Отказ от кумулятивной средней. При создании заготовки или партии пользователь должен видеть список доступных остатков (конкретные закупки или заготовки) и выбирать, что именно используется. Израсходованные позиции не отображаются.
- **Справочник видов заготовок:** Названия и типы заготовок должны выбираться из отдельного справочника, а не вводиться произвольным текстом в форме создания заготовки.
- **Амортизация оборудования:** Реализовать распределение затрат по объёму. Раз в месяц (или за период) затраты на оборудование делятся на общий объём произведённой продукции (кг/шт), формируя долю в себестоимости.
- **Локализация:** Полный перевод интерфейса (типы, статусы, заголовки) на русский язык.
- **Инфраструктура:** Устранение повторяющихся ошибок в командах shell/git путём фиксации правил в `GEMINI.md`.
